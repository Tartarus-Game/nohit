# 固定 240 Hz 的来源与无伤验收的数学范围

固定 240 Hz 来自本项目的调度包装器，不是 jcw 原项目声明的固定物理频率。原版源码保持不变与原版自然调度保持不变是两个命题。现有 Normal 整局无伤记录在其明确的固定 240 Hz 协议下仍然成立；不能把它扩大成任意刷新率、任意卡顿或全部种子的保证。

本文只审计协议和证据，不修改生产时钟、原版代码、CSV 或物理。源码时序细节见 [原版运行时时间域审计](original-runtime-time-domain-audit-20261006.md)。

## 240 Hz 从哪里进入系统

| 入口 | 具体来源 | 作用 |
| --- | --- | --- |
| `compensate=1`，且无 `oracle` 参数 | `c2-sans-fight/lag_compensation.js:5–6,35,57–65,89` | `FixedStepClock` 默认 `hz=240`，阻止原版自行安排变 dt tick，以 `last_tick_time+1000/240` 调用完整原版 tick，并按墙钟追赶积压 |
| 带 `oracle` 参数的诊断或计算入口 | `c2-sans-fight/engine_oracle.js:4,77,107,470` | 每个动作帧执行四次 240 Hz 原版 tick；准备阶段也使用相同的合成时间戳。即使没有 `compensate=1`，此入口仍为固定 240 Hz |
| TAS 的控制步映射 | `c2-sans-fight/tas_runner.js:52,65–79,847–848` | `PLAN_FPS=60`，按物理 tick 数映射持键长度；注释中的“measured 240 fps”是历史观测，不是原版固定频率设置。该映射函数自身不强制原版调度频率 |

`index.html:164,167,170` 分别加载这些包装器。`engine_oracle.js` 的现有 Git 历史最早在 `67f22d5`（2026-10-05 00:19:25 +0800）已出现固定 240 Hz 调用；之后还有 `a02ca48`、`c1fe6f1`。`lag_compensation.js` 在本次审计的共享工作区仍是未跟踪文件，没有可据以追溯作者意图的提交历史。代码来源能证明实现机制，不能据此推断当时选择 240 Hz 的完整理由。

原版 `c2runtime.js` 通常每次 RAF 回调走一次完整 tick，以实际时间戳差计算 dt；没有将每次 RAF 自动拆为四步。缺少 RAF 时约 16 ms 回退。原版接受 60、120、240 Hz 范围内的 dt，并不意味着三者的完整状态转移等价。

## 为什么更细时间步不等于更精确地模拟同一系统

记完整状态为 s，输入为 u，原版一步算子为 `F(s,u,dt)`。固定时钟 D 的运行满足

`s[k+1] = F(s[k],u[k],D[k])`。

若把一次 dt 拆成两次 dt/2 要保持等价，至少需要在保持同一输入时满足半群条件

`F(F(s,u,dt/2),u,dt/2) = F(s,u,dt)`。

原版不满足该条件。例如 `Battle.xml:5905–5907` 的龙骨退场速度每 tick 增加 30，没有乘 dt。令初速为零、每步先加速再移动，固定频率 f 下有

`v[n+1]=v[n]+30`，`d[n+1]=d[n]+v[n+1]/f`，

从而 `v[n]=30n`、`d[n]=15n(n+1)/f`。同墙钟 t=n/f 下，

`v_f(t)=30ft`，`d_f(t)=15ft²+15t`。

在 0.1 秒处，60、120、240 Hz 的退场位移分别为 10.5、19.5、37.5 像素。频率改变了系统本身的演化，不只是数值误差。入场插值、阈值事件、Timeline 消费及碰撞相位也可能因 tick 分割而变。

因此补偿器是选定一种确定的执行协议。一次 100 ms 卡顿下，普通运行时可能仅执行一个被截到 1/30 秒的 tick；固定 240 Hz 补偿器最终补齐约 24 个 tick。不能称这两种执行在数学上相同。将 `+30` 改写为与 dt 成比例也会改变原版物理，本次没有这样做。

## DAG-DP 和 C-space 应当对什么命题负责

给定初态、源脚本、随机源、时间戳演化 D、输入集合及允许切换时刻，每层的安全递推为

`R[k+1] = { F(s,u,D[k]) : s ∈ R[k], u ∈ U[k], Safe(s,u,D[k]) }`。

C-space 加速 Safe，精确状态商和集合运算加速递推；奖励只改变候选访问次序。优化必须保持同一个 R，不能通过更换 D、丢弃低分路线或拼接不相容的轴边际制造答案。要烘焙攻击，烘焙对象也必须绑定 D 和影响环境的分支状态。

对已声明的有限动作图，完整安全展开为空可证明该图内没有见证；若只展开四 tick 持键、有限来源或有限时间段，结论只覆盖该限制。预算耗尽、域限制以及尚未证实的模型对应关系一律不能作为原版无解证明。

证明某个 D60 存在无伤输入，不能推出 D240 存在无伤输入，反向也不成立。用另一频率寻找见证可以帮助诊断，但不能冒充原目标时钟下的修复。60/120 Hz 的当前审计尚待独立结果，本文不宣称其完整 Real HELL 可解。

## 已完成的 Normal 无伤证据仍然成立

[独立验收结果](../tools/real-game/full-game-verdict-20261006.json) 为 `passed=true`、`errors=[]`：seed=42，24 回合、24 个现场候选、0 次失败尝试，23 次成功 FIGHT；原生 tick 11 至 68252 共 68242 步核查，54413 个计划覆盖步与实际输入一致。

[整局实现进度](full-game-progress-20261006.md) 已明确该记录是固定 240 Hz 补偿协议下，从开场到真实 Win2 的完整 Normal 战役无伤运行。时间域审计没有推翻这份观测，也没有将其重新定义成其他频率的测试。其源哈希证据是保存时文件哈希，而不是对浏览器已加载字节码的独立哈希，此限制也已在验收文件中说明。

本机无 oracle、无 compensate 的原版菜单曾在约 2002.4 ms 内推进 420 tick，约 209.75 tick/s。这个有抖动、并非完整逐 tick 序列的菜单样本，只能反驳“自然运行严格固定 240 Hz”的断言，不能代表战斗时钟或替代整局验收。

下一步应首先闭合所声明时间协议下的源码算子、编译几何与严格可达性证据，再决定需要覆盖哪些实际调度情形。数学优化优先的含义是保持命题与状态集合不变地减少工作，而非先改变时钟使路线出现。
