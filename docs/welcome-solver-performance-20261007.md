# welcome_to_hell：实现性能与原版语义诊断

**2026-10-07 当前结论：`welcome_to_hell.csv` 已在原版运行时完整无伤通过。**
从新 Custom attack 入口执行 1464 个物理 tick（48.8 游戏秒），实际触发原版
`EndAttack`；全程 HP92、KR0，无正伤害事件。随后空输入运行 12 tick，障碍保持为空、
场地缩放完成，正常返回 FIGHT 菜单。没有修改 CSV、游戏状态、伤害规则或恢复存档。

原先 CPU 使用不足确实来自实现开销；此外发现了透明度比较、输入初态和结尾对话语义缺口。
这些已有具体测量或原版反例，不能以“数学递推正确”替代实现验真，也不能把资源上限直接
解释成状态爆炸或原文件无解。Real HELL 的完整可解性不由本次 welcome 结果决定。

## 完整原版验证与执行协议

成功路线是 `scratch/welcome-30-continuation/all0-beam3000-seed42-dialogue.json`。
主路线从真实初态重新生成，没有借用旧路线、前缀或预设 GetHeartPos 目标；尾段明确搜索
移动键和 Confirm。原版每 tick 注入移动 mask 与独立的 Z/Confirm 布尔值，按原事件表
推进对话，不能把 Confirm 的 bit32 交给只接受 0..31 的旧移动接口。

这次验证采用明确的 **30 Hz 物理协议**：给完整原版 tick 的时间戳为
`last_tick_time + 1000/30 + 1e-6` 毫秒，让原版自身的最大 dt 夹值产生精确 `1/30` 秒。
没有直接写入 dt。入场后的第一次完整帧记录为 model tick0，`actions[0]` 从下一帧执行；
全部输入和物理 tick 连续向前，没有 checkpoint 分支或状态重置。这证明该协议下的整关
无伤路线，不是任意变化帧率或所有机器实时调度的鲁棒性结论。

含初态在内的 tick0..1463 共 1464 个 11 维玩家状态，与模型逐字节一致。最后 tick1464
的区别来自原版 `EndAttack` 把心移回 FIGHT 并重置最大落速；原版同时清空攻击对象。
原生事件顺序为 `TLpause`1444、`TLresume`1447、`TLpause`1448、`TLresume`1463、
`EndAttack`1464，HP/KR 和所有移动、确认输入均已逐帧核对。

## 240 Hz 的具体障碍证书

旧捕获时钟下，完整 reset-family 前沿使用精确去重和并行扩展，在四 tick 持键语言中
于 tick2228 穷尽；将末段输入细化到每 tick 后，tick2226 的 762 个状态在 tick2227 的
全部 12,192 个后继仍被同一条 x259 竖直激光拒绝。这不是预算上限。

更强的几何证书不依赖 DP 状态数量：tick2204 的四条有效激光将无伤中心限制在
`287.25 < x < 350.75`、`274.25 < y < 337.75`；同 tick 的左向重摔设定 dx=-750。
到 tick2227 的 23 步内，没有平台、传送、缩框、后续重摔或可触及的墙面改变该速度。
因此即使允许整个连续安全矩形作起点、每 tick 任意选择方向，仍有
`x < 350.75 - 750×23/240 ≈ 278.875`，而避开该束要求 `x > 280.860573789118`。
对边界外放 `1e-9` 后仍矛盾约 **1.98557 像素**。

这是冻结的捕获时钟模型证书，不能扩大成原 CSV 在所有原版执行条件下无解。详见
`scratch/bottleneck2227-audit/corridor-certificate.json`、同目录 `README.md`，以及
`scratch/exact-frontier-dedup/REPORT.md`。旧原生前缀只观测到 tick2212；证书本身不是
缺失原生 tick2227 的实测替代品。

时钟改变了这条束的实际离散事件时间，而非仅改变搜索采样密度：原版 ENTER 使用
`v += (destination-v)*dt*10`，随后按剩余距离小于 3 像素到位；倒计时的零比较也按帧发生。

| 该束事件 | 捕获 240 Hz 模型 | 恒定 30 Hz 模型及成功原生路线 |
| --- | ---: | ---: |
| 开始伤害 | tick2154 / 8.975 s | tick267 / 8.900 s |
| 左向重摔 | tick2204 / 9.183333 s | tick276 / 9.200 s |
| 取消伤害 | tick2233 / 9.304167 s | tick276 / 9.200 s |

240 Hz 下重摔后激光还伤害约 120.833 ms；30 Hz 下同束在重摔当 tick 已无伤害。
`scratch/bottleneck2227-audit/clock-comparison.json` 保存对应生命周期，完整 30 Hz 原生
验证已跨过这个窗口。因此帧率不能作为没有证据的推托；这里的解释是可复核的具体事件
顺序与几何约束。30 Hz 成功也不意味着原 240 Hz 协议已经被解开。

## 原版透明度语义修复

原版 Construct 2 的 `CompareOpacity` 比较前执行六位小数舍入，
而模型直接比较原始浮点值。捕获时钟下的 `80.00000000121096`
在原版应比较为 80，旧模型错误地多保留一个 tick 的激光伤害。
伤害清除位于原版 PlayerDamage 事件之前，因此不是观察相位不同。

生产 `compact_wave.py` 已按原版归一化、夹值及舍入后比较。
正式新增回归修复前 3 失败 / 1 通过，修复后相关测试 **119 通过**。
生产模型对 2213 次原版观察的 11 个激光数量差异全部消失，顶点最大误差 `2.27e-13`。
完整原版源码定位见 `scratch/native-opacity-isolated/README.md`。

修复不改变 tick2200–2225 的即时几何，但改变了更早边界以及后续2226、2232、2233。
因此不能断言它与全局可达路线无关，也不能据此宣称已经找到搜索失败的唯一根因。

## 多核与状态数量分别测量

四个独立进程、不同软排序、每个 100k 节点的试验：
墙钟 11.667 秒、累计 CPU 45.609 秒，实际使用 **3.909 个核心**。
四个运行均到资源上限，最深 tick2220，没有候选路线。
这是排序组合试验，跨进程状态重叠未量化，不能说完成了 400k 个互不重复状态的探索，
也不是已经集成的并行 DP。证据：`scratch/welcome-parallel-probe/report.json`。

单进程 20k 状态中的计数：

- 尝试 164,116 条边，43,627 条因碰撞拒绝。
- 120,489 条安全边中，100,490 条命中已证明死状态，约 83.4%。
- 接纳 19,999 个后继加初态，恰有 20,000 个唯一键，重复接纳次数为 0。

现有精确去重有效，但生成将命中 dead 的后继本身仍有计算成本。
这些数据没有测出全局状态空间的大小，不能把资源限制归因于已经证明的“状态爆炸”。
当时下一步是测量状态分布和搜索覆盖，以及能减少重叠工作的并行划分；后续证书见上文。

进一步记录这次 20k 运行的完整状态后，只为统计将 x/y/dx/dy 舍入至 9 位或 6 位，
保持 tick、环境和其他键字段完全相同，两种统计仍各有 20,000 个组，最大组大小为 1。
同组条件下最近状态对约相差 0.625 像素；本次已观察状态不是浮点尾差造成的碎片。
**97.35% 的展开集中在 tick2120–2212（8.83–9.22 秒）**，栈上 534 个节点尚有未试动作。
这明确暴露了深度优先枚举在较晚局部分支上消耗预算的现象；它不证明其他分支有解。
