# 原版运行时的时间域审计

**原版没有固定 60 Hz，也没有固定 240 Hz。它通常由浏览器 RAF 触发，按实际时间戳差计算 dt。代码中存在真正按 tick 而非按秒更新的物理量，因此不同帧率下的攻击轨迹并不相同。**

这不代表 240 Hz 非法，也不能把切换成 60 Hz 当成解决当前 240 Hz 问题。主任务在本机无 compensate、无 oracle 的原版 MainMenu 做了 2002.4 ms 只读观察：tickcount 增加 420（平均约 209.75 tick/s）；轮询取得 335 个 tick，dt 最小约 0.0039、中位约 0.0042、最大 0.0085 秒。这是高刷新率但有抖动的自然运行，不能称严格 240 Hz，也不是 60 Hz。轮询漏了部分 tick，不能当完整 dt 序列；该样本来自菜单，不是战斗。本脚本未另测实机。主任务记录在 `docs/mathematical-optimization-contract-20261006.md`。

## 源码证据

- `repo_jcw87/Bad Time Simulator (Sans Fight).caproj` 没有固定逻辑 60/240 Hz 的项目设置。
- 原版 `c2-sans-fight/c2runtime.js` 第 88 行选择 `requestAnimationFrame`；第 122–125 行 `mb` 每个回调执行一次 `ux`，没有自动把一次 RAF 细分成四个物理 tick。没有 RAF 时使用约 16 ms 的 setTimeout 回退。
- `jcw_adapter.js` 映射 `tick=mb`、`dt=De`、`dt1=df`、`last_tick_time=dk`，仅作为本审计阅读压缩代码时的名称映射。
- 运行时初始化 `Eq=30`、timescale `Jf=1`。时间更新为：令 `δ=max(0,(timestamp-last_timestamp)/1000)`；若 `δ>0.5`，`dt1=0`；否则 `dt1=min(δ,1/30)`；`dt=dt1*timescale`。游戏时间累计 dt，wallTime 累计原始 δ。60/120/240 Hz 的 dt 都在原版正常接受范围内。
- `lag_compensation.js` 第 57–65 行抑制自调度的变 dt tick，第 89 行注入 `last_tick_time+1000/240`，每次走完整原版 tick。积压债务逐步追赶，不丢逻辑 tick；暂停/隐藏期间重新锚定墙钟。

因此卡顿补偿保留了**选定的固定 240 Hz 逻辑协议**，但它不是对任意原版 RAF 时间序列都等价的渲染优化。例如一次 100 ms 卡顿，普通运行时只执行一个 dt=1/30 的 tick；补偿器最终执行 24 个 dt≈1/240 的 tick。两者推进的游戏时间和逐 tick 更新次数均不同。

## 哪些更新依赖帧率

| 机制 | 原版表达式或行为 | 时间域影响 |
| --- | --- | --- |
| 龙骨退场速度 | `LeaveSpeed += 30`，Battle.xml 5905–5907，SID 1907195994494986 | 明确每 tick 增量，没有 dt；同秒加速度随 Hz 成比例改变 |
| 龙骨退场位移 | 按 `dt * LeaveSpeed` 反方向移动 | 乘 dt 无法抵消速度增量漏乘 dt；继承上行的帧率差异 |
| 龙骨入场 | `v += (target-v)*dt*10`，距离小于 3 时吸附 | 离散欧拉迭代，分成两步通常不等于一次大步；进入 WAIT/FIRE 的时刻还被 tick 边界量化 |
| 玩家重力与跳跃 | 速度更新 `Gravity*dt`，重力按速度区间及输入条件选择；CustomMovement 在事件表输入更新之前推进 | 不存在上面那种漏 dt 的四倍加速度，但离散积分、区间切换、按键上升沿和碰撞相位仍依赖 tick 分割 |
| 骨刺、平台、战斗框、普通骨头 | 多数位移乘 dt，边界判断/反向/出生/销毁每 tick 执行 | 匀速自由移动可按总 dt 对齐，碰撞或事件边界附近不能一般地合并 tick |
| 激光宽度 | 增长乘 `dt*30`，收缩乘 `0.8^(dt*30)`；阈值按 tick 检查 | 纯收缩区间的指数因子可组合，但增长/满宽/消失阈值与 FIRE 开始时刻量化仍不同 |
| Timeline | 本 tick 先消费已满足的延时，随后 `T += dt` | 同一 CSV 指令发生在不同帧率的不同离散边界，且同 tick 可消费多个指令 |
| 字幕和震屏 | 计时器累加 dt；达到 1/30 后每 tick 最多处理一次字符/强度递减 | 是阈值事件，不应误称无条件每 tick 加速；不构成当前攻击几何的单独证明 |

脚本还输出 116 项不含 dt 的动作清单。该清单包含命令触发、攻击编号递增、动画周期回绕等，**不能把所有这些动作都说成每 tick 物理更新**。本轮明确确认的无 dt 连续物理增量是 LeaveSpeed。

## 严格反例：更细 tick 不是同一运动的更精确采样

固定频率 f、dt=1/f，从已 FIRE、初速 0 且尚未出界的龙骨开始。令每次先更新速度，再移动，原版给出

`v[n+1] = v[n] + 30`，`d[n+1] = d[n] + v[n+1]/f`。

所以 `v[n]=30n`、`d[n]=15n(n+1)/f`。在相同墙钟 t=n/f 下，

`v_f(t)=30ft`，`d_f(t)=15ft²+15t`。

这不是收敛到同一个连续系统的普通离散误差；f 增大时，主项本身增大。令 t=0.1 秒，实际调用共同 `_ActiveGasterBlaster.step` 的结果为：

| Hz | tick 数 | 退场速度 px/s | 退场位移 px |
| ---: | ---: | ---: | ---: |
| 60 | 6 | 180 | 10.5 |
| 120 | 12 | 360 | 19.5 |
| 240 | 24 | 720 | 37.5 |

若把原始 `+30` 改成 `+900*dt` 或 `+1800*dt`，那是选择一个参照帧率并**修改物理**，不再是忠实复现原始事件表。本轮没有做这种修改。

## 原版 Real HELL 的同墙钟比较

复现命令：`tools\uv_py.bat scratch/audit_realhell_time_domain.py`。

脚本只在离线模型中从同一 pre-TLPlay 环境重新初始化，分别给定数学常数 dt=1/60、1/120、1/240，沿原 CSV 编译到 6.5 秒。结果为 `scratch/realhell-time-domain-audit.json`，包括完整几何快照、source hash、命令事件和公式断言。没有改变服务或实机时钟，也没有执行搜索。

一批六条 GasterBlaster 加两条 BoneStab 指令在 60/120/240 Hz 下分别于模型墙钟 `6.183333`、`6.175000`、`6.170833` 秒被执行。定义墙钟为完成 n 个 dt 后的 n/f，首 tick 也包含在内；不要直接将这个常数 dt 试验的 tick 编号混用为先前精确二进制时间戳重放的编号。

下表是在每个频率的同墙钟处，按原版合法红心中心范围（战斗框边界内缩 5+8 px），采样 19600 个整数位置，检测 4×4 伤害判定框与白骨、伤害激光的重叠后剩余的点数。蓝骨按静止规则排除。它只描述这一时刻的空间切片，**不是可达状态，不是路线，也不是可解性证书**。

| 6.30 | 654 | 847 | 847 |
| 6.35 | 412 | 466 | 466 |

6.30 秒三者都是六个白矩形和五个伤害激光，数量相同并不表示坐标或之前的可达历史相同。表内若干点数相等也不能推出空间集合相等，更不能推出动态可达集合相等。

## 对“原版有解”的精确定义

把实际时间协议写作 D=(dt0,dt1,...)，完整状态转移写作
`s[k+1]=F(s[k],u[k],dt[k])`。
对固定 D 的无伤命题是存在输入序列 u，使每一步满足该时钟下的安全谓词。证明 D60 下存在 u，并不蕴含 D240 下存在对应输入；同样，某个 D240 搜索耗尽预算也不推出 D60 或 D240 无解。

当前固定 240 Hz 的原版线性验收仍然是**原版运行时在明确 240 Hz 调度协议下**的有效证据；需要保留这一限定。自然 RAF 约 240 Hz 与严格固定 240 Hz 也不完全相同，前者有 dt 抖动及边界相位差异。把“源码未变”“原版在这一时钟下执行成功”“所有合法帧率都可解”区分开，才能让求解和验收的数学命题闭合。

本轮没有证明 60、120 或 240 Hz 的完整 Real HELL 可解，也没有更改现有 240 Hz 任务目标。
