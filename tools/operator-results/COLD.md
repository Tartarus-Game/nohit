# 冷处理测量与构建边界

2026-10-05，Windows 本机，BoneGap1 / seed42 / 完整时域 / beam3600 / 相同安全余量。用户要求关注冷处理，因此热进程算子实测不再作为冷启动结论。

| 条件 | 实测耗时 | 解释 |
|---|---:|---|
| 新进程，空编译缓存，B 首解 | 14,608.56ms | 含导入、编译、预烘焙、搜索及进程启动退出 |
| 其中 CSV 几何预烘焙 | 82.56ms | 不能把其余十几秒归入几何烘焙 |
| 其中首次预处理含编译 | 4,020.14ms | 距离场算子的 JIT 成本 |
| 其中首次搜索含编译 | 9,550.68ms | DAG 搜索算子的 JIT 成本 |
| 本机 CPU 构建产物服务冷启动到就绪 | 1,142.70ms | 新进程，只加载机器码，请求期禁止编译 |
| 服务第一次新路线请求 | 383.90ms | HTTP 墙钟，路线缓存关闭 |
| 其中首次几何预烘焙 | 146.75ms | 重新解析原版 CSV、光栅化及碰撞盒膨胀 |
| 启动加第一次新路线请求 | 1,526.60ms | 尚未稳定达到 1s 以内 |

证据：`cold-b-empty.json`、`cold-service.json`。独立新进程的 A/B 首解证据在 `cold-a-built.json`、`cold-b-built.json`；它们包含进程退出成本，与常驻服务到首响应的测量口径不同。构建产物首解记录 compiled_code_hits=2、compiled_code_misses=0、route_cache=false。

编译没有凭空消失：本机 CPU 构建两个 dtype 的快核耗时约 24.41s，现在发生在显式 `tools/build_kernels.py` 构建步骤。此前通用 CPU 构建约22.18s，但求解较慢，已改用本机 CPU。再次构建未改源码只加载已有机器码，不能拿该缓存命中耗时冒充首次构建。若要求源码交付、机器码产物也完全为空，当前 Numba 路线仍需十几秒 JIT；真正免首次编译的发行方案还需固定运行时和可分发的原生二进制。

服务端还去掉了旧的 T=1 预探测烘焙。完整时域直接由同一次 CSV 解析确定，避免重复解析与一次额外光栅化。

预构建仅解决已校准快核的冷启动。RandomBlaster2 原版快照搜索约 60s，以及平台、旋转/摔落、玩家依赖瞄准等机制的候选覆盖仍有独立瓶颈，不能据此宣称所有回合冷解均已达到 1s。报告里的 15ms/1ms 保持目标身份。

机器码产物在 `build/kernels`，不包含时空张量或动作序列；按本机 CPU、源码、时间戳、Python 与依赖版本验证。源码变化会提示显式重建，而不会在用户请求里隐式等待编译。
